acceptance_criteria: lib/ledger.sh's ledger_mark increments consecutive_failures for any non-ok envelope status and flips the engine to failing at engine_fail_threshold, with no distinction for a CAPABILITY REFUSAL. When agy declines a diff over agy_max_bytes it is doing exactly what plugins/engines/agy/run is designed to do and says so clearly, yet it counts toward disqualification — so an engine that reviews small diffs perfectly would eventually be skipped for everything, including the work it is good at. Observed live in r-001: agy refused a 100777-byte diff by 777 bytes and the ledger recorded consecutive_failures 1 with last_status failed. Distinguish a capability refusal from an engine fault, end to end: the adapter must be able to say which it is, and the ledger must not count the former. Add a focused test that a capability refusal leaves consecutive_failures unchanged while a genuine fault increments it. MANDATORY OPERATOR HAND-OFFS for this task, not optional: the implementer profile cannot execute anything (lesson L017), so it must NOT re-pin Formula/orchid.rb, must NOT chmod any file, and must NOT be asked to run a verifier, shellcheck or bash. It must instead state plainly in its report that the formula pin is stale, that verification was not run, and — ONLY IF this task actually adds a new executable — that its mode needs setting. Do not report a chmod hand-off when no executable was added. The operator performs those three and records them. The focused test must assert BOTH fields, not just the counter: a capability refusal must leave consecutive_failures unchanged AND must not record last_status as failed, since resolve_role_available and the status ledger both read that field and a refusal mislabelled as a fault still misleads an operator reading orchid status.
